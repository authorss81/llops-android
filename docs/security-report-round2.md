## Detail

### [R2-B1D-02] Restore accepts a structurally-invalid or EMPTY SQLCipher database and swaps it over the live vault — irrecoverable data loss with the app's own HMAC re-armed on attacker data (independent crypto duplicate folded: R2-B1C-01)
- **Status:** open → **triaged to fix-phase 135** (2026-08-17, generated by phase-119)
- **Severity:** MEDIUM
- **Area:** Batch 1 · Data-at-rest & DB (also reported by the crypto agent as
  R2-B1C-01 — same root cause, merged here)
- **Agent:** b1-datarest (+ b1-crypto duplicate)
- **Evidence:** `ImportExportService.kt:1867-1932` (`validateAndPrepareRestoredDb`),
  `:1281-1289` (`checkRestoredSchemaNotNewer` only rejects NEWER `user_version`,
  so a 0 < 9 DB passes), `:1816-1860` (`extractBackupEntriesTo` — no minimum
  size/content check; a crafted 0-byte `noteflow.sqlite` sets `sawDatabase = true`),
  `:1979-1982`/`:2017-2022` (delete/update sanitizers swallow "no such table" errors),
  `:1711-1722` (`rekeySqlcipherDb`), `:1801-1808` (`rearmBaselineFromFile` HMACs the
  restored copy — re-blessing attacker data), `:2086-2125` (`commitRestoredFiles` swaps
  + `deleteRecursively()` deletes the only surviving copy); `NoteflowDatabase.kt:416-417`
  (`fallbackToDestructiveMigration()` — a restored DB with a mismatched Room identity is
  silently DROPPED on the next open). The only pre-swap gates are SQLCipher candidate-key
  open + `PRAGMA integrity_check == ok` + `user_version <= SCHEMA_VERSION`, all of which
  a freshly-initialized EMPTY SQLCipher DB satisfies (`integrity_check` = ok, `user_version`
  = 0, `PRAGMA rekey` materializes the header so the file is non-empty by re-arm time).
- **Exploit scenario / Reproducer:** An attacker who knows the vault master password
  (the backup password — household/coworker share or an ex-partner) mints a valid NFLB3
  archive containing an empty/zero-schema `noteflow.sqlite`; the victim restores it via
  the normal restore flow or from a craftable WebDAV folder. Every note/stroke/
  voice-note/version is irreversibly replaced by an empty vault — no "this backup
  contains no data" warning, no quarantine of the live file. Less maliciously: restoring
  a backup exported from a fresh install silently wipes a populated vault. A wrong-schema
  (not version 9) restored DB additionally hits `fallbackToDestructiveMigration()`.
- **Fix:** Before the swap, open the restored DB under the successful candidate key and
  (a) require the expected Room schema (`pages`/`strokes`/`note_versions`/`media_embeds`
  tables exist in `sqlite_master`), (b) refuse `user_version` outside an accepted range
  (absence = empty backup, require explicit confirmation), and (c) warn/refuse on a zero
  rowcount vault unless the user confirms "start fresh". Abort the restore (quarantine the
  incoming file) rather than re-arm + swap on any failure.

- **Severity:** MEDIUM

- **Agent:** b1-applogic
- **Evidence:** the guard `writeGuardedAgainstLock`/`isLockRacedWrite` exists but is used
  only at 3 sites (`NoteflowViewModel.kt:3177` util def, `:3187`, comment `:3170-3176`
  scopes it to "the non-flush page writes (create/rename/tag/daily/wiki/template)").
  Bare `viewModelScope.launch { repository.X() }` with no catch: `updateNotebookTags`
  `:1728`, `deleteNotebook` `:1736`, `addSection` `:1750`, `renameSection` `:1758`,
  `deleteSection` `:1767`, `updatePageTags` `:1971`, `renameTag` `:1980`, `deleteTag`
  `:2007` (vault-wide scans `:1984-2024`), `togglePinPage` `:2032`, `trashPage` `:2038`,
  `updatePageTemplate` `:2047`, `restorePage` `:2260`, `deletePagePermanently` `:2266`
  (also FS-deletes audio embeds, `NoteRepository.kt:843-849`), `movePage` `:2278`,
  `emptyTrash` `:2284`, palette ops `:2290-2306`. `lock()` disposes the pool
  (`NoteflowViewModel.kt:3668-3673`, comment `:3657-3660` "fail closed ('connection pool
  has been closed')").
- **Exploit scenario / Reproducer:** Default auto-lock fires (1 s idle poll,
  `MainActivity.kt:248-263`) or the user taps "Lock Vault Now" racing a just-tapped
  destructive/iterate-heavy action (`renameTag`/`deleteTag` scan the whole vault); the
  in-flight DAO call hits the disposed pool and throws an uncaught
  `IllegalStateException("connection pool has been closed")` into the `viewModelScope`

  this delta; the tag/trash/pin/template/notebook/section paths were left out.

### [R2-B1A-02] In-flight vault search is never cancelled or fail-closed on lock — same pool-closed crash, and a completed search can still deliver decrypted results after auth dropped
- **Status:** open → **triaged to fix-phase 134** (2026-08-17, generated by phase-119)
- **Severity:** MEDIUM
- **Area:** Batch 1 · App logic & auth (search job vs `lock()`)
- **Agent:** b1-applogic
- **Evidence:** shared `searchVaultJob` `NoteflowViewModel.kt:2098`; cancelled only on a
  new keystroke (`:2101`, `:2116`), NEVER in `lock()` (`:3638-3694` — no
  `searchVaultJob?.cancel()`). `deepSearchPages` (`NoteRepository.kt:550-564`) pages the
  DAO on `Dispatchers.IO`; `searchPages` re-loads the corpus (a `zeroizeKey()` →
  `invalidateSearchCorpus()` path) — both hit the pool `lock()` disposed, throwing into an
  uncaught launch. `onResult` (`:2105`, `:2120`) is guarded only by `ensureActive()`,
  which returns normally if the job just isn't cancelled, so a completed search can still
  publish a decrypted `List<NotePageEntity>` after the auth gate dropped (consumed behind
  the LockScreen — low secrecy impact, but a post-auth write to UI state).
- **Exploit scenario / Reproducer:** Fast typist + 5-min auto-lock: the polling lock fires
  while a deep search decrypts on `Dispatchers.IO`; the page-batch DAO call throws on the
  closed pool → crash, or (with a faster finish) decrypted results land in `_searchResults`
  after the vault locked.
- **Fix:** `lock()` should `searchVaultJob?.cancel()` + clear `_searchResults`; the search
  launch should re-check `_authenticated` before invoking `onResult`.

### [R2-B1D-01] Startup tamper-verify is structurally guaranteed `Mismatch` after any write since the last baseline stamp — the WAL-aware HMAC tripwire can no longer distinguish real tampering from an ordinary note edit (regression-of-design on B1-DB-6 / phase-87)
- **Status:** open → **triaged to fix-phase 136** (2026-08-17, generated by phase-119)
- **Severity:** MEDIUM
- **Area:** Batch 1 · Data-at-rest & DB (B1-DB-6 regression-of-design)
- **Agent:** b1-datarest
- **Evidence:** WAL journal mode `NoteflowDatabase.kt:415`; HMAC streams main + `-wal`
  (`DatabaseHmacPolicy.kt:42-66`, `DatabaseSecurityHelper.kt:49-72`); verify runs once per
  process at init (`NoteflowViewModel.kt:1138-1150` → `1202-1223` → banner
  `MainActivity.kt:321-332`); the ONLY re-arm sites are event-driven — `NoteflowViewModel.kt:1116,1490,1517,1561,2634,3348`, `HomeScreen.kt:586,1398` — none on the normal write path; `lock()` (`NoteflowViewModel.kt:3638-3694`) and `NoteflowDatabase.dispose()`
  (`:431-436`) never checkpoint + re-arm. A vault used since its last backup/migration/
  password-armed baseline therefore fails the next-start verify whether a last-connection
  close checkpoint merged the WAL (main differs) or not (wal bytes differ).
- **Exploit scenario / Reproducer:** Create master password (baseline armed) → write/edit a
  note → next process start: the persistent "Database integrity check failed" banner shows,
  and `DatabaseIntegrityVerdict.Mismatch` can never be trusted as a tamper signal again —
  the same banner a real attacker would trigger is now routine. Per-session dismissal is
  the only relief; the door it closes (B1-DB-6) is effectively half-open (a real tamper
  hides in the noise).
- **Fix:** Checkpoint + re-arm the baseline at every session end (`lock()` / dispose) or
  verify only at a quiescent checkpointed state (fresh unlock, post-checkpoint, before
  writes), so a verified pass has meaning again; alternatively drive the baseline from a
  stable per-record construction (e.g. HMAC over a snapshot header) instead of raw main+wal
  bytes. Re-assert the B1-DB-6 coverage tests against the new cadence.

### [R2-B1P-01] Clipboard-scrub on lock covers only 2 of the app's copy surfaces — the primary note-editor copy is untracked and survives every lock (B2-UI-2 gap)
- **Status:** open → **triaged to fix-phase 139** (2026-08-17, generated by phase-119) → **FIXED in phase 139** (2026-08-18, `workspace/phase-139/REPORT.md`)
- **Severity:** MEDIUM
- **Area:** Batch 1 · Android platform surface (B2-UI-2 gap)
- **Agent:** b1-platform
- **Evidence:** `ClipboardGuard.recordCopy()` is stamped at exactly two sites —
  `OcrResultDialog.kt:149` and `MediaEmbedComponents.kt:353`. `lock()` scrubs via
  `scrubIfOwnCopy` (`NoteflowViewModel.kt:3649`) which denies when `mostRecentCopyAtMs
  == 0L` (`ClipboardGuard.kt:50-54`, `ClipboardScrubPolicy.kt:32-33`). The markdown editor
  is a platform text field (`HybridMarkdownEditor.kt:219`) whose long-press → Select-all →
  Copy writes decrypted note body to the system clipboard with NO `recordCopy()` stamp; the
  OCR dialog's own `SelectionContainer` (`OcrResultDialog.kt:121`) has the same untracked
  native Copy next to the tracked button.
- **Exploit scenario / Reproducer:** User copies a note body via the normal editor selection
  menu → taps "Lock Vault Now" (or auto-lock/screen-off fires). `scrubIfOwnCopy` sees no
  stamp and wipes nothing; the LockScreen shows but the decrypted note text is still on the
  shared clipboard — a bystander pastes it in any app. Unlike the 60 s window caveat of
  B2-UI-2, these copies have NO window at all.
- **Fix:** Route every note-content copy through ONE shared stamping helper (intercept the
  editor selection via `LocalTextToolbar`/custom `SelectionContainer`), or — given this
  app's threat model — clear the primary clip unconditionally in `lock()` instead of only
  "own copy within window". Grep-pin that every clipboard write in `ui/` is preceded by
  `ClipboardGuard.recordCopy()`.
- **Fix applied (phase-139):** the UNCONDITIONAL-clear option was chosen. `lock()`
  (`NoteflowViewModel.kt:4057`, scrub at `:4073`) now calls
  `ClipboardGuard.scrubUnconditionally(appContext)` (new method, `ClipboardGuard.kt:84`,
  shared private `clearPrimaryClip` `:88`) which clears the whole primary clip — no
  stamp check, no window — so the untracked native note-body copy paths (editor
  `OutlinedTextField` selection Copy, `HybridMarkdownEditor.kt:219`; OCR
  `SelectionContainer`, `OcrResultDialog.kt:121`) can never survive a lock. The windowed
  own-copy decision stays on the ON_PAUSE hook (`MainActivity.kt:154`,
  `ClipboardGuard.scrubIfOwnCopy(this)`) so a brief app switch still never wipes a
  foreign copy; API 26-28 `setPrimaryClip("")` fallback retained. Both existing stamped
  sites keep `recordCopy()` (ON_PAUSE defense-in-depth). Grep-pin:
  `B2Ui2ClipboardScrubTest.every note-content copy stamps the guard…` now ENUMERATES every

  `every production clipboard write is routed through the guard…` pins that raw
  `{set,clear}PrimaryClip` exists only inside `ClipboardGuard.kt`. Tests: `B2Ui2ClipboardScrubTest`

### [R2-B1D-05] `exportBackup` copies the live main DB file with a plain unbounded FileInputStream — a concurrent auto-checkpoint can produce a torn/corrupt archive
- **Status:** open → **triaged to fix-phase 137** (2026-08-17, generated by phase-119)
- **Severity:** LOW
- **Area:** Batch 1 · Data-at-rest & DB
- **Agent:** b1-datarest
- **Evidence:** `ImportExportService.kt:1314-1318` (`exportBackup` copies
  `noteflow.sqlite` with a plain `FileInputStream` copy; only `-wal`/`-shm` also captured),
  vs the checkpoint-first producers `HomeScreen.kt:584-588` / `NoteflowViewModel.kt:3346-3350`
  (`checkpointWal()` BEFORE the backup). The WAL auto-checkpoint threshold (1000 pages)
  can fire DURING the copy.
- **Exploit scenario / Reproducer:** A large active vault where the WAL auto-checkpoints
  (reclaiming frames + rewriting main) mid-copy yields a main-file snapshot that never
  existed — a torn archive that only surfaces at restore time (`integrity_check` fails →

  checkpoint immediately before, racing the copy itself.
- **Fix:** Read the DB file under the same `getPagePermanently`-safe discipline — e.g. a
  full `checkpointWal(FULL)` + open a live SQLCipher backup source (`PRAGMA backup_to`,
  `SQLiteDatabase.database.copyToFile`) so the snapshot is consistent; or open the file for
  copy while holding a read lock after a fresh FULL checkpoint and verify size+HMAC on the
  staged copy.

### [R2-B1D-04] v2/v3 restore decrypt holds the <=400MB encrypted input AND <=400MB decrypted zip concurrently (~800MB peak), then extraction hits a LOWER 200MB cap — legitimate large vaults are unrestorable and the path OOMs mid-restore leaving the DB closed
- **Status:** open → **triaged to fix-phase 138** (2026-08-17, generated by phase-119) → **FIXED in phase 138** (2026-08-18, `workspace/phase-138/REPORT.md`)
- **Severity:** LOW
- **Area:** Batch 1 · Data-at-rest & DB
- **Agent:** b1-datarest
- **Evidence:** `ImportExportService.kt:1563-1636` (in-heap decrypt: encrypted
