# Phase 76 — B2-DEPS-04 (MEDIUM): downloadable-plugin signing key

**Status:** DONE (2026-08-16)

## Finding recap

`plugins/llm/build.gradle.kts` shipped a committed plugin-signing **default
password** and, when `PLUGIN_SIGNING_KEYSTORE_B64` was unset, minted a **fresh
self-signed JKS every build** with `keytool -genkeypair`. Because the pin
authored by `pluginMetadata` was the hash of "whatever key was used", the trust
anchor was self-referential (hash of a key generated seconds earlier), and the
committed default meant anyone with source could sign official-looking plugins.
Additionally the `:app:generateLlmPluginSeed` task the comment claimed consumes
that pin did not exist anywhere — the compiled-in pin was always absent.

## What changed (before → after, with file:line)

### `plugins/llm/build.gradle.kts` (module = `:plugins:llm`)

- **DELETED:** `DEFAULT_KEY_PASSWORD = "inkflow.2026.plugins"` (was `:147-148`),
  the `keytool -genkeypair` fallback (was `:150-175`), the
  hardcoded-password `loadSigningCert` fallback (was `:177-184`), and the
  fallback-password jarsigner path (was `:186-212`). No branded/default key
  bytes remain in the file — the leaked credential is gone from source.
- **ADDED — fail-loud env requirements:**
  - `requirePluginSigningKeystoreB64()` (`:159-172`) — throws
    `GradleException("LLM plugin signing refused (B2-DEPS-04): PLUGIN_SIGNING_KEYSTORE_B64 is unset. …")`
    when the env var is missing.
  - `requirePluginSigningStorePass()` (`:173-183`) — same treatment for
    `PLUGIN_SIGNING_STORE_PASS`.
  - `pluginSigningKeyPass()` (`:185-192`) — optional `PLUGIN_SIGNING_KEY_PASS`,
    else the required store password. Never a committed constant.
  - `PLUGIN_SIGNING_TASK_NAMES = { signPlugin, verifyPluginSignature, pluginMetadata }`
    + `gradle.taskGraph.whenReady { … }` (`:195-204`) — refuses the whole build
    **before any task executes** when either env var is unset and a plugin-signing
    task is on the request. Mirrors the `:app` phase-57 release-signing gate.
- `pluginSigningKeystore` (`:217-225`) now only decodes the base64 JKS from the
  env (`Base64.getDecoder()` → `build/plugin-signing/plugin-signing.jks`); there
  is no generation fallback. `loadSigningCert()` (`:228-232`) and `signPlugin`
  (`:238-267`) use the required store/key passes; `signPlugin`'s jarsigner
  invocation (`:252-…`) is a pure-literal executable arg list (no secrets in
  `commandLine` flags beyond the pass args the task already reads).
- **FIXED latent bug found while executing this phase:** `signPlugin` used to
  list `pluginSigningKeystore` (a `Provider<RegularFile>`) in its `dependsOn`.
  Gradle hard-errors on that (`Cannot convert … plugin-signing.jks to a task`),
  so signing could never run even with a keystore present. The keystore is now
  materialized **inside** the task action
  (`pluginSigningKeystore.get()` at `:243-245` → bytes written at `:246`) and is
  no longer a task dependency. In scope because it is the very path this phase
  targets; documented here per PROMPT.md "new related bug → document, fix".

### `app/build.gradle.kts` (module = `:app`)

- **ADDED — the previously nonexistent `:app:generateLlmPluginSeed` task**
  (`:248-327`): `dependsOn(":plugins:llm:pluginMetadata")`, so it inherits the
  fail-loud signing gate (no keystore env ⇒ the metadata task cannot build).
  It reads `plugins/llm/build/plugin-artifact/plugin-metadata.properties` (via
  `Properties`, new `import java.util.Properties`), validates every field is
  present and well-formed — `sha256` must match `^[0-9a-f]{64}$`
  (`:262-264`), `pinnedCertHash` must match `^sha256/[A-Za-z0-9+/=]+$`
  (`:265-267`), `version` must be `major.minor.patch` (`:268-270`) — and
  rewrites `GeneratedLlmPluginPin.kt` with those values (`:293-…`). Not wired
  into `assembleDebug`; it is an operator/CI publishing task only.
- The generated file header carries `AUTO-GENERATED by `:app:generateLlmPluginSeed`
  — DO NOT EDIT BY HAND`; the committed seed stays `null` until a real release
  exists.

### `app/src/main/kotlin/com/authorss81/noteflow/plugins/runtime/GeneratedLlmPluginPin.kt` (NEW)

- `internal val llmPluginSeedRelease: PinnedPluginRelease? = null` (`:22`) —
  fail-closed placeholder, overwritten only by the seed task from a
  **signature-verified** build.

### `app/src/main/kotlin/com/authorss81/noteflow/plugins/runtime/CompileTimePluginPinStore.kt`

- `CompileTimePluginPins.RELEASES` (`:195`) now folds the committed seed:
  `CompileTimePluginPinStore.buildReleaseTable(*listOfNotNull(llmPluginSeedRelease).toTypedArray())`
  (was `emptyMap()`). With the seed `null` the table stays empty — the update
  chain refuses every offer exactly as before; with a real pin committed, the
  app can only ever accept the version signed by that ONE key identity.

## Checksum / secrets handling

- `PLUGIN_SIGNING_KEYSTORE_B64` (base64 JKS) and `PLUGIN_SIGNING_STORE_PASS`
  come only from the operator/CI secret store. `PLUGIN_SIGNING_KEY_PASS` is
  optional and defaults to the store password. Nothing is logged; no key is
  compiled into a debug or release artifact.
- The trust anchor ships as **source** (`GeneratedLlmPluginPin.kt`), produced by
  the seed task from a signature-verified `pluginMetadata` — never as a binary
  keystore. The positive-path test keystore was a throwaway in `/tmp` and was
  deleted; the seed was reverted to `null` before commit. No keystore is
  committed (pinned by test 7).
- Repo-wide scan: the leaked credential bytes and `keytool`/`-genkeypair`
  patterns exist ONLY in `.md` files (findings/evidence quoting); the build,
  source, and test trees are clean.

## API-floor / compatibility

No runtime code changed, so the API 26+ floor is untouched and no runtime
fallback is needed. The change is pure build-time security policy (Gradle/task
config) + one nullable Kotlin value consumed by the existing pure-JVM pin store.
