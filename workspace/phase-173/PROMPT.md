## Feature 1 — Serve the FileTransfer capability over LocalSend

`PluginCapability.FileTransfer` is STILL unserved — `PluginCapabilityDirectory`
(`services/PluginCapabilityDirectory.kt`, phase-157) honestly reports it as
`UNSERVED`, and any request fails loudly with `NO_PLUGIN_INSTALLED`
(`PluginRegistry.kt` / `PluginManager.kt`). Wire a REAL `FileTransferPlugin`
whose implementation sends a note (or the encrypted vault backup, or an
Obsidian/HTML export) to a nearby device via the EXISTING LocalSend protocol
v2.2 sender (`services/localsend/LocalSendSender.kt`) — the exact payload
kinds HomeScreen's ⋮ menu already offers. Reuse the LocalSend strings/assets
and the sender's consent flow; do NOT add any new permission.

Design constraints:
- Reuse `LocalSendSender` (Protocol v2.2) — do not fork it. Expose its
  `sendFile(...)`/discovery through the plugin's capability API.
- The plugin must fail CLOSED (respect `PluginManager` fail-loudly semantics)
  and must NOT bypass the human-consent step ("receiving device must accept
  before bytes move", as the protocol already does).
- Keep opt-in semantics: plugin does nothing unless the user enables it
  (default OFF) — consistent with every other compile-time plugin.
- Pure-JVM testability: a `FileTransferPluginPolicyTest` (or extend
  `LocalSendProtocolTest`) proving the plugin maps capability calls to the
  expected LocalSend messages/endpoints without touching the network.

Definition of done Feature 1: `PluginCapabilityDirectory` now lists FileTransfer
as served; an enable-able `FileTransferPlugin` is registered; tests cover the
routing/consent mapping; `assembleDebug` green. Update `docs/PLUGINS.md` (the
"still-unserved" list changes to Assistant-only until the LLM plugin is
installed).
